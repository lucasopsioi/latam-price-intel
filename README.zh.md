# 拉美竞品情报中枢

在你本机常驻运行的竞品情报系统：**每天自动抓取拉美六国渠道价格 → 多 Agent 清洗审计 →
竞品对照 / 上市看板 / 情报流 → Telegram 简报**。

覆盖 **墨西哥 / 巴西 / 哥伦比亚 / 智利 / 秘鲁 / 阿根廷**，
五大产业 **手机 / 穿戴 / 音频 / 平板 / PC**，22 个友商品牌，31 个渠道（启用 29）。

---

## 快速开始

1. 双击 **`1-install.bat`** —— 装依赖 + 下载浏览器内核 + 建库（首次约 150MB）
2. 装开机自启（**推荐，只需一次**）：右键 `tools\install-service.ps1` →
   用 PowerShell 运行。装完桌面上会出现 **「拉美竞品情报中枢」** 图标。
3. 在 **设置** 页填 API Key（见下方「必须配的两个 Key」）
4. 在 **渠道健康** 页点「开始体检」，先看清楚哪些渠道当前能抓
5. 在 **我的产品** 页下载模板，填好导入 —— 竞品匹配需要它才能算

## 常驻运行（24 小时在线）

装好之后不用管它：**开机登录 40 秒后自动启动，无窗口，掉线自动拉起。**

| 你想干什么 | 怎么做 |
|---|---|
| 打开看板 | 双击桌面图标（服务没起会自动拉起再打开） |
| 看现在健康不健康 | http://127.0.0.1:8765/api/health |
| 看守护日志 | `logs\supervisor.log` |
| 看服务日志 | `logs\server.log` |
| 手动重启 | `powershell -ExecutionPolicy Bypass -File tools\restart.ps1` |
| 卸载自启 | `powershell -ExecutionPolicy Bypass -File tools\install-service.ps1 -Uninstall` |

### 三层结构

```
计划任务 LatamIntelHub（登录后 +40s，父进程 svchost.exe）
   └── tools/supervisor.py  守护进程（常驻，单例）
          └── main.py serve  真正的服务（:8765）
```

**为什么要这么绕**：以前是用前台 .bat 或 `nohup &` 起服务，那样服务是**终端会话的
子进程**，窗口一关、会话一断，整棵进程树跟着死 —— 2026-08-15 掉线 11 小时就是这么
没的（日志无 traceback、无优雅关闭，同一秒所有 Chrome 会话齐断）。
现在祖先是计划任务，跟任何终端都没关系。

### 出事了会怎么通知你

- **服务进程崩了** → 秒级发现，退避 5s 后重启，发 Telegram；**恢复后再发一条**
- **服务假死**（端口通但查不动库）→ 探针 60 秒一次，连续 3 次失败才重启（避免误杀正在跑重活的进程）
- **外网断了** → 报警但**不重启**（重启治不好断网）；采集会空转，这个必须让你知道
- **Telegram 没配 / 发不出去** → 兜底写 `logs\ALERT-最近一次故障.txt`
- **点图标但起不来** → 等 90 秒后弹窗，把最近 12 行服务日志贴给你

报警只在**状态翻转**时发，连续故障用指数退避（5s→15s→60s→3min→10min）——
断网一夜收几百条等于没有报警。

> 健康探针**真的会查一次数据库**，不是只看端口通不通。
> uvicorn 的端口在依赖就绪之前就已经监听了，库锁死 / 磁盘满 / schema 没迁移的时候
> 端口照样答应 —— 只看端口会一路绿灯而界面全白。

> ⚠️ **不要用 `Restart-ScheduledTask`**。实测它在这个任务上**什么也没做** ——
> 守护和服务的 PID 一个都没变，日志里连一条新启动记录都没有，而且**不报错**。
> 原因是任务设了 `MultipleInstances=IgnoreNew`：Stop 是异步的，紧跟的 Start
> 在旧实例还没退干净时被直接忽略。用 `tools\restart.ps1`，它会验证新进程真的起来了
> （检查 uptime 是否够小），而不是看到端口有响应就宣布成功。

### 已知边界

- 触发器是**登录时**而不是**开机时**。开机触发要跑在 SYSTEM 账户（session 0），
  那里没有用户桌面和 Chrome 配置，Selenium 直接废掉；而且注册它要管理员权限，
  当前账户没有。**所以：开机后需要登录进桌面，服务才起。** 不登录只是黑屏待机，
  不算"开着"。
- 电脑睡眠/休眠时服务跟着睡，醒来自动继续（`StartWhenAvailable` 已开）。

## ⚠️ 先读这一节：渠道的真实可用性

这些不是"理论上支持"，是 **2026-08-10 从本机实测出来的**。
渠道会随站点改版和风控策略变化，所以内置了 `doctor` 体检命令，
任何时候可以重测。

### 2026-08-11 最新实测（以本节为准，下面的历史表保留破解过程）

四个长期抓不到的渠道做了并行探测 + 独立复验：

| 渠道 | 结论 | 做法 |
|---|---|---|
| **Alkosto CO** | ✅ 已解决 | 站点是 Hybris 外壳，但商品网格是**前端 Algolia 渲染** —— 服务端 HTML 里只有 4 个商品，其余 76 个根本不在页面上（这才是"只认出 4/80"的真因，不是选择器不好）。改走 Algolia 索引，手机品类 **466 个商品** |
| **Fast Shop BR** | ✅ 已解决 | 新域名 `site.fastshop.com.br` **完全可达、无任何人机验证**；之前 empty 是因为搜索页纯客户端渲染（402KB HTML 里 "R$" 出现 0 次）。改走 **VTEX Intelligent Search** 接口 |
| **Ripley PE** | ⛔ 被拦，需你本人过一次验证 | Cloudflare **Managed** Challenge 整站 403（连 robots.txt 都是 403）。智利站好好的是因为它是 `non-interactive` 挑战、真实浏览器几秒自动过；秘鲁站是 `managed`，可升级为需真人点 Turnstile。**本系统不做任何绕过验证的事** —— 要开通请用 `tools/site_login.py`，你在可见浏览器里过一次，系统只复用 cookie |
| **Shopee BR** | ⛔ 无公开可读路径，保持停用 | 决定性证据：四个完全不同的路由（首页 / 搜索 / sitemap.xml / 商品页式路径）返回的 HTML **字节完全相同**（同一个 MD5）—— 服务端对任何 URL 只吐同一个 SPA 骨架。正规开通路径是申请 Shopee 官方开放平台 API |

> 顺带修掉一个**我们自己的**误诊：体检把"解析为空"一律翻译成「选择器失效，去修适配器」。
> Ripley PE 就是被这条误导的 —— 真因是没过挑战。
> 现在 `empty` 只报「原因待查」，并在下结论前先做拦截特征判定。
> **一个自信的错误诊断比"不知道"有害得多。**

### 关于 Coppel 那种失败 —— 本系统最重要的一道防线

Coppel 页面正常返回 200，解析器正常解析出 11 条带价格的商品，
体检报告会显示 **「OK 11条」**，看起来比被风控拦截的 Liverpool 还健康。

但那 11 条是首页推荐位的**锐步运动鞋和 Spring Air 床垫**。

如果直接入库，运动鞋的 899 MXN 会进入手机价格基线，把中位价拉到地板上，
之后所有竞品比价与异常剔除全部失真 —— **而且不报错**。

所以系统内置了 **搜索结果相关性校验**（`app/scraping/relevance.py`）：
整批相关率低于 34% 判定为「搜索未生效」，整批作废并标记 `irrelevant`，
与「该渠道确实没这个品牌的货」（`empty`）严格区分开。

> 抓不到数据你知道没数据；抓错了你以为有数据。后者危险得多。

## 必须配的两个 Key

### 1. MercadoLibre Access Token（最重要）

ML 是六国都有的最大电商，**阿根廷更是只有这一个渠道**。

实测结论（本机 + 上一代系统共 8 轮验证）：**ML 对未登录访客强制 302 到
`/gz/account-verification`，headless / 有头 / 换设备全部撞墙** ——
这是访客策略，不是浏览器指纹问题，换设备再多次也过不去。

三条通道，系统自动降级：

| 通道 | 怎么开 | 效果 |
|---|---|---|
| ① 官方 API | developers.mercadolibre.com 免费注册拿 token，填进设置页 | **推荐**。官方授权通道，不过人机验证墙、零封禁风险、字段最全（含官方店标识/库存/分期） |
| ② 登录态 Cookie | 跑 `python tools/ml_login.py MX`，在弹出的浏览器里**你本人登录**（建议用可弃的普通买家号） | 软件不读不存账号密码，只存会话 Cookie，几周过期后重跑 |
| ③ 游客网页 | 无需配置 | 大概率直接撞墙，会如实报 `login_wall`，不做无谓重试 |

### 2. MiniMax API Key

清洗 / 价格审计 / 情报三个 Agent 用它。**不配也能跑**，但会退回规则模式：
灰色地带的价格判不了、新闻不翻译不打分、页面文本兜底抽取不可用。

## Agent 排布

**所有 Agent 共用你在设置页填的 MiniMax 订阅 Key**，可以 24 小时不间断跑。

```
调度器 Orchestrator
    │
    ├─① 中央主 Agent (chief)      抓之前先研判：读渠道健康档案，
    │                             判定每个渠道该正常抓 / 降频 / 换引擎 / 跳过
    │                             → 产出 crawl_plan（带研判理由，界面可查）
    │
    ├─② 采集 (collector)          按计划驱动 Selenium/Playwright，不调大模型
    │
    ├─③ 清洗 (cleaner)            LLM 兜底抽取 + 型号归一化 + 挂接友商产品
    │
    ├─④ 价格审计 (price_audit)    剔除第三方溢价 / 配件误判 / 翻新 / 错价
    │
    ├─⑤ VOC (voc)                 抓评论 + 翻译分析 + 好评/差评点提炼
    │                             + ★高评论量归因（真热销/上市久/大促冲量/
    │                               质量吐槽/刷评 —— 五种含义完全相反）
    │
    ├─⑥ 规格补全 (spec_filler)    补齐芯片/屏幕/内存 —— 竞品匹配的必要输入
    │
    ├─⑦ 竞品匹配                  三规则硬闸 + 排序分
    │
    ├─⑧ 情报 (intel)              扫全球 top 科技站 + 六国新闻，
    │                             发现新品、判重要度、记录上市节奏
    │
    └─ 竞争动态四件套（喂「竞争动态」看板与「竞品周报」页）
        ├─⑨ 价格变动 (price_move)  **不调 LLM**：同 SKU 同渠道同币种比价，
        │                          检出真实涨跌，官方渠道与第三方分开记
        │                          （官网降价是厂商动作；第三方降价可能只是卖家甩货）
        ├─⑩ 价格策略 (strategy)    从变动模式推断厂商意图：老品清库 / 新品前降价 /
        │                          大促铺垫 / 成本涨价 / 价格战
        ├─⑪ 品牌动态 (brand_intel) 追踪经营动作：开体验店、发布会、渠道合作、进退市场
        └─⑫ 周报汇总 (weekly)      把一周的变动/信号/动态汇总成给 销售团队 看的中文周报
```

分层是有意的：**⑨ 是事实层（纯计算），⑩⑪ 是解读层（调模型），⑫ 是汇总层**。
"哪个 SKU 涨跌了多少"交给模型既慢又不可靠；模型的价值在推断意图，不在算术。

**实时看得见**：界面「实时过程」页会滚动显示正在搜哪个渠道、抓到了什么价格、
哪里被拦了。跑 10~20 小时的长任务也可以随时回来看进度。

**每一步都留痕**：`agent_step` 表存下送进模型的提示词、模型原始回复、
解析结果、判定结论与理由。界面「Agent 编排」页点开任意一次运行，
能看到"这个价格为什么被剔掉"的完整链条。

选流水线而不是"中央大脑动态派活"的理由：**可复现、可单独重跑**。
某个 Agent 挂了不影响已完成的阶段。

## 权威 SKU 表

`config/sku_rules.yaml` 是从用户既有的 PowerQuery（SKU_Short）移植来的
**人工维护穷举映射表**：272 条规则 → 131 个 SKU，覆盖平板品类。

它是**权威口径**，优先于通用型号归一化 —— 系统的数字要和用户既有报表对得上账。

三条硬约束（改这张表前必读 `app/skumap.py` 的模块注释）：

1. **行序即规则**：取第一个匹配，所以必须从最具体排到最泛化。改行序 = 改结果。
2. **key 的前后空格有意义**：`'ipad 8 '` 的尾部空格是为了不匹配 `ipad 80`。
3. **只覆盖平板**：`skumap.COVERED_CATEGORIES`。跑手机品类时必须传 category
   过滤掉，否则每个单元白跑 8 次无关查询（实测会多烧 6 小时）。

**保证覆盖的做法**：光搜「tablet Samsung」抓不全 ——
一次搜索只返回二三十条，热销款会把长尾挤掉。
所以每个 SKU 名单独作为一条搜索词（Samsung 平板 30 个、Apple 38 个、Xiaomi 21 个）。

**输出字段**：`sku_code` / `ram_gb` / `rom_gb` / `list_price`（划线价）/
`sale_price`（实际售价）/ `discount_pct`（off 力度）。
折扣在**入库时**算，区分「明确没打折」(0.0) 与「算不出折扣」(NULL) ——
查询时现算会把两者糊成一样。

## 反爬设计

**主引擎是 Selenium (undetected-chromedriver)，Playwright 兜底。**

实测依据：Liverpool 在 Playwright 下冷却换设备重试两次仍被拦死（每轮白耗 120 秒），
Selenium 一次通过拿到 56 条、只用 24 秒。undetected-chromedriver 直接给 chromedriver
打补丁抹掉自动化特征，比 Playwright 的 CDP 通道更难被指纹脚本识别。

代价是慢 2~4 倍 —— 但目标是**24 小时内跑完且不被封**，不是跑得快。

**一律以安卓手机/平板身份访问，绝不用桌面网页版。**

为什么只模拟 Android 不模拟 iPhone：程序内核是 Chromium，Android 真机浏览器
就是 Chrome，UA 与 JS 引擎指纹天然自洽；伪装 iPhone 反而会因
"Safari 外衣 + Chrome 内核"的矛盾被指纹脚本识破 —— 弄巧成拙。

| 手段 | 做法 |
|---|---|
| 设备模拟 | 7 档安卓机型（含拉美市占高的 moto g84 / Redmi Note 13），每 N 页轮换 |
| 本地身份 | 按国家配 locale / 时区 / Accept-Language 三件套 |
| Cookie 持久化 | 每国一份，第二天像"回头客"访问 |
| 动线拟真 | 先逛首页暖场 → 带自然 Referer 进搜索页 → 触摸滚动 + 随机停顿 |
| 封锁自愈 | 命中验证 → 冷却 60~150 秒 → 换设备 → 全新会话重试一次 |
| **双引擎兜底** | 同域被**主引擎**连拦 3 次后自动切到另一个引擎；渠道也可用 `force_engine` 单独指定 |
| 登录墙识别 | 单独识别，**不做无谓重试**（换设备也过不去，硬闯只会拉黑 IP） |
| **拟真停留** | 变速滚动、对数正态分布的停留时长、18% 概率回滚、随机 mousemove |

关于拟真停留：机器人最明显的特征不是速度，是**规律** —— 每次滚一样的距离、
间隔一样、从不回头、看完就走。所以停留时长取对数正态分布（多数很短、偶尔很长），
并加入回滚与鼠标移动（有些风控会统计 mousemove 事件，一次都没有的会话很可疑）。

### 页面加载策略必须用 eager

Selenium 默认 `pageLoadStrategy=normal` 要等 `load` 事件 —— 也就是所有图片、
广告 SDK、追踪像素全部加载完。拉美电商挂着一堆第三方广告脚本，任何一个慢就拖到超时
（**实测 Liverpool 首页在 normal 下 45 秒超时**）。改 `eager` 只等 `DOMContentLoaded`，
商品数据那时已经在 DOM 里了。超时也不当失败：`window.stop()` 停掉剩余请求继续解析。

## 数据正确性上的几个关键设计

**1. 价格解析按国家分币种走不同分支。**
巴西/阿根廷 `1.234,56`（逗号是小数点）、墨西哥/秘鲁 `1,234.56`（相反）、
智利/哥伦比亚 `$1.234.567`（无小数位，点全是千分位）。
同一串 `1.234` 在墨西哥是 1.234，在智利是 1234 —— **差一千倍**。
`tests/test_extract.py` 有 57 项回归断言锁死这些边界。

**2. 异常价基线的分组键 = 国家 × 型号 × 月，一个都不能少。**
少了国家维度，阿根廷 895,999 ARS 和巴西 3,499 BRL 会被当成同一尺度比较，
整个高汇率国家被判成异常（上一个项目实测：剔掉了 59% 的行、中位数偏 85%）。
**剔除率本身是健康度指标：超过 1% 先怀疑分组键写错，而不是先信结论。**

**3. 详情页 JSON-LD 不能盲取第一个。**
商品详情页几乎都有"相关推荐"区块，那些商品各自带 JSON-LD Product。
取错就把价格记到别的产品名下。系统会用价格接近度 + 标题词重叠校验归属，
两条都不满足就宁可少补几个字段。

**4. 竞品判定的三条规则是「与」不是加权和。**
规格再像但价差三倍不是竞品，是不同价位段的产品。
所以做成"硬闸 + 排序分"：可得性/价格带/规格分任一不达标直接出局，
达标的再按 `0.45×规格 + 0.35×价格 + 0.20×可得性` 排序。

**4.5 官方自营 vs 第三方卖家必须分清，且判据在"缺失"里。**
Liverpool、MercadoLibre、Amazon 都是自营/官方店与第三方混卖。
第三方常有溢价、水货、翻新 —— 实测抓到一台**翻新** S23 Ultra 挂 9,987
（原价 23,999），不区分就会报成"降价 58%"。

★ Liverpool 的判据是**标签的存在性**：实抓 56 个商品卡片只有 1 处
`Vendido por` 标签 —— **marketplace 商品才标商家，自营的什么都不标**。
第一版在整页文本搜 "liverpool" 当官方标识，而页头页脚到处是这个词，
于是**全站商品含第三方一律判成自营**，两类被混成一类且看不出错。

Amazon 还要分开 `Vendido por:`（卖家）与 `Enviado por:`（配送方）——
"第三方卖家 + 亚马逊配送"很常见，把配送方当卖家会把大量第三方误判成官方。

**5. 规格缺失退出计算，不当成 0。**
把缺失当 0 会让"未知芯片"变成"最差芯片"，于是所有规格不全的机器都被判成
不是竞品 —— 静默的系统性偏差。正确做法是按剩余权重归一化，
并把"有多少维度参与了比较"作为置信度一起报出来。

**5.2 诊断本身也会误诊 —— 把 A 故障报成 B 故障最耽误事。**
六国 26 渠道体检后复核 5 个不通的渠道，**两个是误诊**：

- Alkosto 报「搜索没生效，必须修 search_url」，但 URL 完全正常（110 价 / 80 商品链接）。
  真相是解析器只认出 4/80 条，那 4 条恰好是边角推荐位 ⇒ 相关率 25% ⇒ 整批作废。
- Ripley 秘鲁报「解析不出，需专用适配器」，但页面标题是 `Un momento…` ——
  Imperva 的**西语**挑战页。拦截词表只有英文 `just a moment`，
  漏了西语变体 ⇒ 挑战页被当成"正常但没商品"，且不触发冷却换设备重试。

三条对策：批级判定的样本量下限从 4 提到 8（4 条做统计判定没有意义）；
新增低产率检测把"解析器坏了"和"搜索没生效"分开报；
拦截词表补齐西语/葡语变体 —— **拉美站点的挑战页是本地语言的**。

**5.5 归一化会往两个方向出错，实测两种都遇到了。**

*裂开*（不足）：颜色被当成型号，`Z Flip8 Crema` 与 `Z Flip8 Rosa` 成了两个产品。

*合并过度*：`S26+` 的加号被当成捆绑分隔符剥掉，与 `S26` 并成一个 ——
两个价位段混算，**实测算出 88% 的假价差**。
区别在于空格：分隔符的 `+` 两边有空格（`Tab S11 + Keyboard`），
型号的 `+` 紧贴前一个词（`S26+ Dynamic`）。

还有一类是**跨渠道对不上**：Sears 写 `Celular Samsung A07`（省略 Galaxy），
Liverpool 写 `SAMSUNG Galaxy A07`，归一化后一个 `A07` 一个 `Galaxy A07`。
必须补全省略的产品线前缀 —— 但只在有把握的品牌上做，**补错比不补更糟**。

**6. 型号归一化会把一台机器裂成好几个产品。**
第一版归一化的真实输出是 `Z Flip8 Crema` 和 `Z Flip8 Rosa` —— 颜色被当成了型号，
同一台 Galaxy Z Flip8 变成两个产品，价格对比直接散架。
剥离顺序不能换：`括号尾巴 → 屏幕技术短语 → 颜色 → 营销噪声 → 品牌名`。
屏幕短语必须整体剥（"Super AMOLED plus" 逐词剥会剩下孤零零的 plus），
品牌名必须最后剥，且**只剥品牌主名不剥型号前缀**（剥掉 Galaxy 后跨品牌会撞车）。

**7. 详情页缓存必须把参与去重键的字段一起缓存。**
详情页结果缓存 7 天以控制请求量，但第一版漏缓存了标题 ——
缓存命中日标题退回成列表页的短版本，`row_hash` 随之改变，
同一商品每天新增一行，**幂等性静默失效、数据翻倍**。

**8. 模型补规格必须防编造。**
问"某某手机用什么芯片"，模型不知道也会给一个听起来很像的答案。
三层防护：强制不确定填 `null`、要求同时给出**可验证锚点**（发布年份 —— 连年份都
不确定说明不熟悉这款产品）、`spec_confidence` 落库并传导到竞品匹配评分。
