# VOC 情报站：20 个建设方向

给拉美 销售团队 用的消费者之声（VOC）情报体系。每条含：**回答什么问题 → 数据源 →
实施路径 → 可行性（已实测/未实测/已排除）→ 工作量**。

**可行性图例**
- ✅ 已实测可行（本次真跑过请求）
- ⚠️ 未实测，路径清楚但要先验证
- ⛔ 已排除，附原因

**排除清单（先说不能做的，省得反复讨论）**

| 源 | 原因 |
|---|---|
| Amazon BR/MX | robots.txt **点名** `ClaudeBot`/`Claude-Web`/`Claude-User` 全站 Disallow。已停用该渠道 |
| Trustpilot | robots.txt 点名 `anthropic-ai` + `CCBot` 全站 Disallow |

| 任何需要过人机验证的站 | 不解验证码、不伪装绕过。要开通只能由**你本人**用 `tools/site_login.py` 过一次 |
| **Apple App Store 评论**（原方向4） | ⛔ **我判错了，已更正**。`itunes.apple.com/robots.txt` 的 `User-agent: *` 段里 `Disallow: /search*` 和 `Disallow: /*/rss/*` —— 正是搜索接口与评论 RSS 这两个端点。绕到 apps.apple.com 也没用（评论走 `/v1/*`，同样被禁）|

| MercadoLibre **网页版** | robots.txt 把 ClaudeBot/Claude-User 与 GPTBot 并列共用 `Disallow: /`（六国全站禁）。**官方 API 不受此限**，配 token 即可 |
| Hiraoka（秘鲁） | robots.txt 具名禁 ClaudeBot，已停用 |

> 这几条不是保守，是同一条线：**站方点名对我们说不之后，继续抓就得伪装成别的东西**。

## A. 零售评论（现有基础，先把它做实）

### 1. 把现有零售评论抓全并结构化
**问题**：友商某款机在某国的口碑到底怎么样？
**源**：Falabella(CL/CO/PE)、Ripley、Liverpool、Paris、Alkosto、Fast Shop 的商品评论区
**路径**：`app/scraping/voc.py` 已有去嵌套/去界面文案/解析作者与相对日期的能力（434 条已入库）。
缺的是**覆盖率**——目前只抓了 132 个商品页。改成"每轮采集后，对当轮价格观测里
**评论数最多的 N 个商品**补抓评论"，N 随时间预算调。
**可行性**：✅ 已实测（现有管线在跑）
**工作量**：小（改调度逻辑，不新增解析器）

### 2. MercadoLibre 评论（六国最大盘，但要 token）
**问题**：ML 是拉美最大电商，缺它等于缺半个市场的声音
**源**：ML 官方 API `/reviews/item/{item_id}`
**路径**：申请 developers.mercadolibre.com 的 access token（免费）→ 用已有的 `MeliAdapter`
拿 item_id → 调评论接口。**走官方 API 就不碰人机验证墙**。
**可行性**：⚠️ 接口存在且 robots 允许（crawl-delay 5s），但**必须你去申请 token**
**工作量**：小（有 token 后半天）

### 3. 评论量当销量代理指标
**问题**：拿不到销量时，谁卖得动？
**源**：已抓的 `review_profile.total_reviews`
**路径**：已实现雏形。要补的是**归因**——评论量高有五种完全相反的含义
（真热销/上市久/大促冲量/质量吐槽/刷评）。现有 VOC Agent 已做这层判断，
但需要评论**日期分布**才判得准（已能解析相对时间）。
**可行性**：✅ 已实测
**工作量**：小

## B. 应用商店与品牌 App（被严重低估的一层）

### 4. ⛔ App Store 评论 —— **已否决，我先前的"完全合规"判断是错的**
**问题**：品牌生态口碑——Acme Health、Samsung Members、Mi Home 的用户在骂什么？
**源**：Apple 官方 `https://itunes.apple.com/{cc}/rss/customerreviews/id={appId}/json`
**路径**：先用 `itunes.apple.com/search?term=acme&country=mx&entity=software` 找到 appId
（**已实测**：返回 ACME Health / AI Life / Audio Connect），再按国家拉评论 RSS。
六国 × 各品牌 App ≈ 60 个源，全部官方提供、无需 key。
**可行性**：⛔ **不可做**。`itunes.apple.com/robots.txt` 的通配段：
```
User-agent: *
Disallow: /search*        ← 搜索接口（找 appId 用的）
Disallow: /*/rss/*        ← 评论 RSS
```
没有点我们的名，但把这两个端点精确禁掉了。**"没点名"≠"允许"**。
★ 我先前只查了"有没有点名禁止本 agent"，没查通配段是否禁掉我们要用的路径 ——
  这是判断方法本身的漏洞，`tools/check_robots.py` 已重写修正。

**还能合法做的（价值低得多，如实说明）**：
- `apps.apple.com/<cc>/app/id<N>` 商品页的 ld+json → 只有**聚合星级 + 评论总数**，
  没有任何单条评论、没有日期。只能做"星级掉了"的告警，说不出为什么掉。
- `rss.marketingtools.apple.com/api/v2/<cc>/apps/top-free/<N>/apps.json`
  → 六国实测全通，但那是**榜单排名**，一条评论都没有。
  ★ 上限是 **100**（n=101 起返回 HTTP 500 且是 HTML，写死 200 会六国全挂）。
- 实测发现：ACME Health 在 MX/CO/CL/PE **根本没上架**（404），只有 BR/AR 有。
  这类 404 必须存成"未上架"状态 —— 当成 0 条评论会得出"墨西哥用户零反馈"的假结论。

**★ 更根本的问题**：拉美安卓占比 ~85%，Acme/小米/OPPO 用户几乎不用 iOS。
拿 App Store 做拉美品牌生态 VOC，**池子本身就选错了**。

### 5. Google Play 评论
**问题**：同上，安卓侧样本量大得多（拉美安卓占比 ~85%）
**源**：Play 商店应用页
**路径**：robots.txt 允许 `/store/apps/details`。评论在页面内嵌 JSON 里。
**可行性**：⚠️ robots 允许，但评论是懒加载，要验证能不能不登录拿到
**工作量**：中

### 6. 运营商 App 评论（拉美特色）
**问题**：Telcel/Claro/Movistar/Entel 的 App 评论里藏着**合约机**的真实体验与投诉
**源**：App Store + Play 的运营商 App
**路径**：同 4/5，但搜索词换成运营商名
**可行性**：⚠️ 路径同 4，未单独验证
**工作量**：小（复用 4 的代码）

## C. 社区与视频（购买决策发生的地方）

### 7. YouTube 评测视频的评论区
**问题**：拉美消费者看西语/葡语评测做决策，评论区是最真实的反馈
**源**：YouTube Data API v3（官方，有免费配额）
**路径**：按「品牌 型号 review/análisis」搜西/葡语视频 → 取 `commentThreads`。
按国家分：用视频语言 + 频道所在地粗分。
**可行性**：⚠️ 官方 API，需申请 key（免费额度每日 10000 单位，够用）
**工作量**：中
**★ 为什么值**：评论区会直接说「比 X 好/差在哪」，这是**竞品对比**的一手语料

### 8. Reddit 国家版块
**问题**：`r/mexico` `r/brasil` `r/chile` 里的真实推荐与吐槽
**源**：Reddit 官方 API（robots.txt 对通用爬虫全站 Disallow，**但官方 API 是允许的路径**）
**路径**：注册 app 拿 client_id → 搜索六国 subreddit + 品牌词
**可行性**：⚠️ 必须走官方 API（网页版被 robots 禁）
**工作量**：中

### 9. 本地科技媒体的文章评论区
**问题**：Tecnoblog/Canaltech/ENTER.CO 的读者评论
**源**：这些站的评论系统（多为 Disqus 或自建）
**路径**：先判断评论是否服务端渲染。**Tecnoblog 的 robots 点名禁了 GPTBot 但没禁我们**
**可行性**：⚠️ 未验证评论是否可取
**工作量**：中

## D. 投诉与消保（拉美特有，且最能预警质量风险）

### 10. ⛔ Reclame Aqui —— **已否决，我先前标的"✅ robots 已实测允许"只查了一半**
**问题**：巴西的品牌声誉是**公开可比**的——每个品牌有投诉量、回复率、解决率、评分
**源**：reclameaqui.com.br
**路径**：robots.txt **允许**，`crawl-delay=10s`（必须遵守）。
按品牌页取：月投诉量、回复率、平均解决时长、投诉分类分布。
**可行性**：⛔ **拿不到数据**。robots.txt 是允许的 —— 但我当时只查了 robots，
没有真的去取一次页面。实测：
- **活站 8/8 全部 HTTP 403**（Cloudflare Managed Challenge，站方在主动反自动化）。
  绕过它就要过人机验证 —— 不做。
- **只有巴西**：`reclameaqui.com.mx/.com.co/.cl/.com.ar/.com.pe` 全部 NXDOMAIN。
  六国里覆盖 1 国。
- 归档（Wayback）里 2025-01 至今**总共只有 4 个品牌快照**（Samsung 1、Motorola 3），
  Apple/Xiaomi/Acme 全是 0。Acme自己史上仅 1 个快照（2021 年）。
- ★ 还有一条不该做的理由：页面上大量指标站方**主动显示成 `--`**
  （"A empresa resolveu --% das reclamações"），而后台 JSON 里有真值。
  把它抓出来入库 = 重新发布源站刻意隐去的数字。

**工作量**：不建议投入
**★ 为什么值**：巴西消费者买贵价电子产品前会查 Reclame Aqui 评分。
这不只是 VOC，**它本身就是购买转化的门槛**——评分低直接掉单。
而且它给的是**结构化指标**（不是自由文本），可以直接做月度趋势与品牌横比。

### 11. Profeco（墨西哥消协）
**问题**：官方渠道的正式投诉与「谁在被点名」
**源**：profeco.gob.mx（robots 允许）
**路径**：Profeco 会公布「Quién es Quién」价格监测与投诉统计
**可行性**：✅ robots 允许，⚠️ 具体数据形态未验证
**工作量**：中

### 12. 各国消保机构的召回/质量通告
**问题**：友商产品有没有被召回或警示——这是**竞争窗口**
**源**：MX Profeco、BR Procon/Inmetro、CL SERNAC、CO SIC、PE Indecopi
**路径**：各机构官网公告页/RSS
**可行性**：⚠️ 未验证各站是否有 RSS
**工作量**：中～大（5 个国家各不相同）

## E. 线下与门店（销售团队 特别关心）

### 13. Google Maps 品牌门店评价
**问题**：「XX 在墨西哥开了体验店」之后，那家店口碑如何？
**源**：Google Places API（官方付费，有免费额度）
**路径**：按「品牌 + 城市」搜门店 → 取评分与评论
**可行性**：⚠️ 需 Google Cloud key（有免费额度）
**工作量**：中
**★ 为什么值**：直接补上你要的「品牌动态：开体验店」的**后续效果**——
开了店之后到底行不行，而不是只知道开了

### 14. 零售商门店页的到店自提信号
**问题**：哪些型号在哪些城市真正铺到了货
**源**：Falabella/Ripley 商品页的门店库存模块（我们已经在解析它）
**路径**：现在这个信息被当成噪声剥掉了（「Sin stock en tienda」）。
反过来用：它其实是**铺货广度**的免费指标
**可行性**：✅ 数据已经在抓，只是没存
**工作量**：小
**★ 顺带修**：之前正是这个字段害我们误判 523 条在售商品缺货

## F. 从已有数据里挖（不需要新数据源）

### 15. 按维度拆解口碑（电池/相机/屏幕/售后）
**问题**：友商这款机到底强在哪、弱在哪
**路径**：VOC Agent 已在提炼好评/差评点，但**没有固定维度**。
定一套维度表（电池、相机、屏幕、性能、发热、做工、系统、售后、物流、配件），
每条评论打多标签 → 可以按国家×品类×品牌出**维度雷达图**
**可行性**：✅ 语料已有，只需改提示词与落库结构
**工作量**：小

### 16. 「提到Acme」的对比语料
**问题**：消费者在什么场景下拿友商和我们比？比的是什么？
**路径**：已实现（`voc_insight.vs_acme`），但只有 1 条命中——因为语料太少。
配合方向 1/2/7 扩大语料后，这条会变成**最有价值的一张表**
**可行性**：✅ 已实现
**工作量**：小（等语料）

### 17. 上市后口碑衰减曲线
**问题**：新品上市后 30/60/90 天，口碑是稳住还是崩了
**路径**：评论日期已能解析（408/434 有日期）。按机型画「首销后第 N 天的平均星级」
**可行性**：✅ 数据结构已具备
**工作量**：小

### 18. 差评 → 质量风险预警
**问题**：友商某批次出问题了吗？（这是**进攻窗口**）
**路径**：同机型同国家的差评**突然聚集**且集中在同一维度（如「发热」），
就触发预警。需要方向 15 的维度标签 + 时间序列
**可行性**：⚠️ 依赖 15 与足够语料
**工作量**：中

### 19. 刷评识别
**问题**：评论量高是真热销还是刷的？
**路径**：现有归因已含这个判断，但缺可计算特征。可加：
评论时间集中度（同一天暴增）、评论长度分布（刷评偏短且同质）、
五星占比异常、作者名模式
**可行性**：✅ 特征都能从已有字段算
**工作量**：中
**★ 注意**：这是**判断**不是事实，输出必须标明置信度，不能直接说「这家刷评」

### 20. 价格变动 × 口碑变动的联动
**问题**：降价是因为口碑崩了，还是降价之后口碑变好了？
**路径**：把 `price_move` 与评论星级时间序列对齐，看哪个先动
**可行性**：⚠️ 需要至少数周的连续数据（目前只有 2 天）
**工作量**：小（代码），但**要等数据攒够**

## 我的建议：分三批做

**第一批（已完成 / 已否决 —— 2026-08-13 更新）**
- ✅ 方向 1（零售评论覆盖）——**已修**，真因是选目标按本币金额排序 ⇒ 等于按币值排名，
  墨西哥候选最多却一个都进不去。改成按国家分区轮转，五国均分。
- ✅ 方向 15（维度拆解）——**已上线**，43 种自由文本维度收敛成 19 个固定维度，
  产品维度与体验维度分开。首个结论：售后好评率 44%，其余维度 88~100%。
- ⚠ 方向 17（衰减曲线）——代码已就绪，**卡在数据**：评论星级覆盖率 0.1%
  （1727 条里只有 2 条有分数），因为零售站把星级渲染成图标而不是文字。
  已加从 DOM 属性读取，**下一轮采集后才有数据**。
- ⚠ 方向 14（门店铺货信号）——探路结论是"能做但别叫它铺货广度"：
  现有样本里门店有货与"卖家=Falabella自营"**100% 共线**（40/40），
  直接做出来其实是在重算一个已有字段；且观测点只有一家默认门店
  （CL 全部是 Cerrillos）。建议改名 store_presence 并按 seller_kind 设限。
- ⛔ 方向 4（App Store）、⛔ 方向 10（Reclame Aqui）—— 见上方排除清单

因为它给的是**结构化的品牌声誉指标**，而不是又一堆要 LLM 去读的自由文本。
